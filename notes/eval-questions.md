# Triveni eval questions (pre-event note)

Status: draft, written Oct 12. Becomes `backend/scripts/eval.py` and `eval/questions.json` at kickoff.
Spec: MVP.md Section 7: 15 questions, 5 per track, scored by exact match on entity sets against `eval/ground_truth.json` (generated by the seed).
Systems: **Triveni** (graph agent with tools over MCP, plus memory) vs **Flat** (TF-IDF top-k over Document text + same LLM, no memory, no graph).
Metrics per track: accuracy (exact set match), answers-with-evidence % (an answer that cites ≥1 source id or path), median latency.

Answer format both systems must return: `{"entities": ["svc:cart-api", ...], "sources": ["doc:pm-0042", ...]}`. The scorer normalizes ids, and the set must match exactly.

Design rule: every question needs ≥2 hops, an algorithm, memory, or currency. If one Document states the full answer, the question is too easy for Flat and gets rewritten. Each row notes why Flat should fail, so the result is a prediction we can check, not a cherry-pick.

## Track 01: Act on connected data

| id | Question | Ground truth (acme) | Needs | Why Flat fails |
|---|---|---|---|---|
| A1 | If payments-api goes down, which services are affected within 3 hops? | {cart-api, orders-api, checkout-web, invoice-svc, refund-worker} | `blast_radius` (DEPENDS_ON*1..3) | dependency facts are spread over many catalog lines; no single doc lists the transitive set |
| A2 | What is the shortest dependency path from checkout-web to payments-api? | [checkout-web, cart-api, orders-api, payments-api] | `shortest_path` | order matters; text retrieval can't chain hops |
| A3 | Which 3 services are most critical by dependency structure? | top-3 of `algo.pageRank('Service','DEPENDS_ON')`, frozen in ground truth at seed time | `critical_services` | needs a global graph computation |
| A4 | Which services have no owning team and no on-call engineer? | {legacy-fax-gateway, pdf-renderer-v1} | `find_orphans` (WCC on RESPONSIBLE_FOR) | proving absence; no doc says "this has no owner" |
| A5 | Can we change the retry policy on orders-api? If not, which decision blocks it? | {blocked, adr:019} | action gate: current Decision GOVERNS + forbids | the stale runbook (rb-orders-retry) says yes, so Flat is likely to answer *wrong*, not just incomplete |

## Track 02: Memory and coordination

Protocol: the harness runs a **session 1** script, restarts the backend process, then asks the questions in **session 2** with a new Conversation id (except B5). The Flat system gets the same session-1 transcript but has no memory store, which is the whole point of the comparison.

| id | Session 1 (setup) | Session 2 question | Ground truth | Needs |
|---|---|---|---|---|
| B1 | (seeded ep:0001) | payments-api has connection timeouts again. Have we seen this before, and what fixed it? | {ep:0001, proc:rollback-payments} | `recall` via shared Service/Incident |
| B2 | (seeded) | What lesson did we learn last time payments-api failed? | {lesson:pool-exhaustion} | Episode → LEARNED |
| B3 | Agent triages inc:0057 (orders-api) and records outcome "resolved by scaling workers" with procedure proc:scale-orders | orders-api is slow again. Which procedure worked before? | {proc:scale-orders} | memory written in session 1, recalled after restart |
| B4 | Triage creates a Handoff about inc:0057 to Remediation | Which open handoffs are waiting for the remediation agent, and about which incident? | {handoff id from session 1, inc:0057} | Handoff nodes (coordination through graph state) |
| B5 | conversation conv:eval-1: user says "I'm on the payments team; call me Ravi" | (same conversation reopened after restart) What team did I say I'm on? | {team:payments} | `load_history` rebuilds context from Message chain |

Isolation check (scored separately, not in the 15): B1 asked on tenant **beta** must return beta's episodes, or none, and never ep:0001.

## Track 03: Company Brain

Protocol: questions C1–C3 run **before** ingesting `chat:billing-move`, and C4–C5 run **after**. The ground truth file holds both states.

| id | Question | Ground truth | Needs | Why Flat fails |
|---|---|---|---|---|
| C1 | Who owns payments-api and who is on call? | {team:payments, per:arjun-mehta}, sources {doc:service-catalog, doc:oncall-schedule} | `owner_of` | answerable from text, so this is a **control** question; Flat should do OK here. Including it is honest |
| C2 | Which decisions govern orders-api today, and which earlier decision did it replace? | {adr:019, adr:007}, sources {doc:adr-019, doc:adr-007} | `decision_trail` (SUPERSEDES + GOVERNS) | both ADRs retrieve; Flat can't tell which is current |
| C3 | Who are the two engineers whose departure would cut knowledge links between teams? | {per:priya-nair, per:dev-malhotra} | `key_people` (betweenness on KNOWS) | requires a global computation |
| C4 | *(after ingest)* Who owns billing-batch now, and who owned it before? | {team:atlas (current), team:ledger (past)}, sources {chat:billing-move, doc:service-catalog} | temporal OWNS + `owner_of` with history | Flat retrieves both docs and has no rule for which wins |
| C5 | *(after ingest)* Which runbooks are out of date for the services Team Atlas now owns? | from ground truth: runbooks MENTIONing a superseded Decision that GOVERNS an Atlas-owned service (post-ingest) | multi-hop: Team → OWNS(current) → Service ← GOVERNS ← Decision ← SUPERSEDES; Document → MENTIONS → old Decision | 4+ hops, plus currency |

C5 requires that the seed plant at least one superseded ADR governing billing-batch, with a runbook still mentioning it (`adr:011` superseded by `adr:023`, `doc:rb-billing-rerun` mentions adr:011). **Add this to the needles table in graph-model.md Section 5.**

## Open points
- Freeze the PageRank top-3 for A3 at seed time and assert it in a test, so a FalkorDB version change can't silently break the eval.
- LLM nondeterminism: run each system 3× and report the mean. Use temperature 0 where the API allows it.
- Under `DEMO_REPLAY=1`, the eval must refuse to run, so recorded results can't inflate the scores.
